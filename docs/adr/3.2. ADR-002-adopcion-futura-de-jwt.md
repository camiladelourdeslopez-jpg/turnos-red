# Título
3.2. ADR-002: Adopción futura de JWT para autenticación y autorización

# Fecha
2026-09-22

# Estado
Propuesto

# Contexto
La API actual no implementa mecanismos de autenticación ni autorización. Los recursos exponidos, como turnos y médicos, son accesibles sin credenciales en esta etapa inicial del proyecto. Esta decisión responde a una fase temprana de desarrollo, donde el foco principal es la funcionalidad del negocio y la documentación del contrato API.

Sin embargo, el sistema puede requerir protección de acceso en etapas posteriores, especialmente si se habilitan operaciones sensibles, permisos por rol o distintos perfiles de usuario. En ese contexto, JWT resulta una alternativa ampliamente adoptada para representar credenciales y permisos en llamadas HTTP.

# Decisión
Se propone evaluar la incorporación de JWT como mecanismo de autenticación y autorización en una etapa posterior del proyecto, una vez definidas las reglas de negocio, roles y alcance del acceso.

La decisión no se implementa en esta fase. La API se mantiene sin seguridad declarada en Swagger/OpenAPI, para reflejar el estado actual del sistema y evitar representar una autenticación inexistente.

# Consecuencias
Positivas:
- permite proteger endpoints según roles o permisos,
- facilita la integración con clientes frontend y terceros,
- ofrece un mecanismo estándar para transmitir identidad y claims,
- mejora la escalabilidad del sistema en entornos productivos.

Negativas:
- requiere definir flujo de login o generación de tokens,
- introduce complejidad de validación, expiración y almacenamiento seguro,
- exige manejo de errores de autenticación y autorización,
- obliga a revisar el impacto de seguridad en endpoints ya existentes.

# Alternativas consideradas
1. Mantener la API pública sin autenticación.
   - Ventaja: rápido, simple y apropiado para prototipos.
   - Desventaja: no escala para entornos con datos sensibles o accesos restringidos.

2. Usar sesiones basadas en cookies.
   - Ventaja: familiar en aplicaciones web.
   - Desventaja: menos apropiado para APIs REST stateless y menos portable para clientes no web.

3. Implementar JWT desde el inicio.
   - Ventaja: prepara la API para seguridad real desde el primer momento.
   - Desventaja: aumenta la complejidad inicial sin estar aún justificada por el alcance actual.

# Limitaciones
- No hay autenticación implementada actualmente, por lo que esta ADR es una propuesta futura.
- La adopción de JWT exige definir explícitamente roles, políticas y expiración de tokens.
- El uso de JWT no debe considerarse una solución universal para todos los escenarios de seguridad del sistema.

# Impacto sobre el proyecto
Este ADR define una dirección futura sin alterar el estado actual del proyecto. Permite preparar la arquitectura para un crecimiento seguro, mientras mantiene la fase actual coherente con la realidad funcional: API pública sin mecanismos de autenticación implementados.
